# Metrics in `openftgs.eval`

How `openftgs.eval` meets its §2.1 row for E16: the image metrics, the dynamic-region crop and mask of App. B.1, the averaging of D-67, and the metrics report that `ftgs eval` writes. The spec gives the module no signatures; its public API is Q-60's. `eval` imports `types`, `data`, `model`, `render` and `losses` from the bands below it, and the private `_shards` for D-54's sharding. The metrics never render: they are pure tensor functions that run on the CPU. `evaluate_images` renders a data split itself, through `render.render_request` (Q-57, Q-68), one request per timestamp, and then scores it ("Evaluating a model on a scene", below).

## The metrics

Every metric takes images in the layout of the losses (Q-41) and returns one value per image. The render is clamped to [0, 1] first (D-67); the ground truth is used as loaded (§1.4).

- **PSNR** takes its MSE in float64, so the value doesn't depend on the order of the reduction (Q-60). A perfect render has an infinite PSNR, which the report writes as null (Q-63).
- **SSIM_k** is the loss's SSIM with data range k, called once per image through the public `losses.ssim`, so the metric and the loss share one definition (E7, E16, D-67). k is 1 or 2. **DSSIM_k** is derived from it (D-29, D-40).
- **ꟻLIP** is NVIDIA's LDR-ꟻLIP, the loss's `PerceptualLoss("flip")` built once by `Evaluator`: the vendored copy at 67.0 pixels per degree, on the clamped render against the reference, the mean of its error map per image (E16, D-89). It needs no weights, so building an `Evaluator` downloads nothing. The value is exactly 67.0, the number E16 and D-89 write, not the published file's default of 67.02, which gives filters of the same sizes but other weights and values about 3·10⁻⁵ away; the harness computes its own ꟻLIP from saved renders at 67.0, and the two agree within U-23's 1e-6 (Q-259). openftgs reports no LPIPS, so its perceptual figures can't be compared with the paper's (E16).

Evaluation is a forward pass in IEEE float32 (D-52): every metric runs under inference mode with cuDNN's TF32 flag cleared and float32 matrix products at "highest" precision, since ꟻLIP's colour transforms are matrix products, and both are restored afterwards; a sharded evaluation sets them once around the whole run instead ("Evaluating on several devices", below). `Evaluator` computes on a float32 copy of the pair, ꟻLIP's only dtype (Q-261), and derives DSSIM_k from the SSIM_k it has just computed (Q-60). On CUDA float32, SSIM₁ may take the fused-ssim path, which agrees with the fallback in value (Q-42).

## The dynamic region

`dynamic_region` turns a render, its ground truth and the test image's mask into the pair that the dynamic-region metrics compare (App. B.1, D-67). The mask is binarized at 0.5, a pixel counting as dynamic at 0.5 and above. The render is clamped, as for every metric; then both images are filled with black outside the mask and cropped to the mask's bounding box, the same box for both (Q-61).

The box is the bounding box of every dynamic pixel, as D-67 defines it, so a single stray mask pixel far from the subject enlarges the crop with black-on-black pixels, which raise PSNR and SSIM and lower ꟻLIP; masks are the user's to supply and clean (D-64), and the package doesn't filter them. A mask with no dynamic pixel, or a box too small to hold every metric's window, gives no pair and a warning, and the report counts that image as skipped (Q-61). The minimum side, 21 px, is the larger of SSIM's 11-px window and the 21 px that ꟻLIP's filters span at 67.0 pixels per degree (three 21×21 spatial filters; 19×19 edge and point filters), as #383 measured them with the vendored copy (Q-61, Q-257). Only SSIM fails below its bound: ꟻLIP pads by replicating the border and gives a value at any size, but below 21 px on a side every pixel of its error map is computed partly from copied border pixels, so the score would measure the padding more than the region (Q-257). Masks come in as bool, or floating in [0, 1]: an integer mask is refused, so whoever reads a mask file (M10's manifest reader, M14's `ftgs eval`) divides an 8-bit mask by 255 first, as §1.4 does for every 8-bit input (Q-61).

## Averaging

Each metric is computed per test image, averaged over a scene's test images, then over scenes, never pooled (D-67). `average_metrics` serves both levels. The paper reports LPIPS with a backbone per dataset; openftgs reports ꟻLIP alone, so the module no longer reads the scene manifest's `metadata.source` for a backbone, and `lpips_backbone` is gone with D-29's LPIPS backbones (Q-62, retired in revision 549o).

## The metrics report

`metrics_report` builds the body of METRICS.json from per-image results and the scene manifest's `metadata` (Q-63). It holds:

- the format tag `ftgs-metrics`, `version` 2, the split and the metric names, psnr, ssim1, ssim2, dssim1, dssim2 and flip, in that order (§2.1, Q-256);
- the full-frame metrics under `entire`;
- the dynamic-region metrics under `dynamic`, when any test image is masked, with the mask source and the approximate flag of D-64;
- under `fastest_10`, the means over the Fastest-10 frames, when the manifest names them (D-69).

`write_metrics` adds the header and writes the file without NaN or Infinity, as every JSON file of the package is written (Q-25). It replaces an existing file atomically: a temporary sibling is renamed over it, so a write that fails partway leaves the old file (Q-126, Q-146). It is the one writer of METRICS.json, for `Trainer.evaluate` and `ftgs eval` alike (Q-136). The header holds `producer`; `model`, as {`path`, `iteration`, `sha256`}, any of which may be null (a trainer's model has no file, hence no path and no hash, and an exchange model no iteration); the hash, 64 lowercase hex digits, is of an exchange model's file or of a checkpoint's `manifest.json`, which holds the SHA-256 of every other file of the checkpoint, so with periodic checkpoints (D-83) it still says which model was scored (Q-136 as answered); and the scene manifest as `manifest` ({`path`, `sha256`}), because `scene` already holds the per-scene means (Q-63). When `ftgs eval` scores supplied renders, a `renders` entry ({`dir`, `request_sha256`, `producer`}) says what was scored (Q-137).

The `dynamic` block counts under `missing` the images of the split that have no mask, 0 for a full set, so a partial set is visible in the report (Q-135); `ftgs eval` and `ftgs train` refuse a partial set before doing any work.

Version 2 is the report since revision 549o. Version 1, which M17's runs wrote and the validation-run records cite, held LPIPS-Alex, LPIPS-VGG and lpips_vgg_raw in place of ꟻLIP, and an `lpips_backbone` label; the package writes version 2 only, and `scripts/run_summary.py` and `scripts/view_renders.py`'s comparison read both versions and say which they read (Q-256). Between files of different versions, the comparison compares the five metrics both versions hold, PSNR, SSIM₁, SSIM₂, DSSIM₁ and DSSIM₂, and lists the metrics one version holds alone (ꟻLIP; the three LPIPS values) once under `not_compared`, with no finding, so that a rerun on an M17 model against its version-1 file reports only real differences (Q-266).

A null in the report means "not defined here": a perfect render's PSNR, a mean over no images, a dynamic region that was skipped (Q-61). It never stands for a failed render, which `evaluate_images` refuses before any report is built (below; Q-129, Q-147).

## The Fastest-10 frames

The selection itself is not in `eval`. D-69 has the converter store the range in the manifest, and the converter is in `data`, which may not import `eval`, so the selection is `openftgs.data.fastest_frames` (Q-59). It streams the test camera's frames and returns the start of the window. M12's converter scores the test camera's frames as it stores them, after undistortion and resizing, so the range can be recomputed from the files (D-69), and maps the start to the manifest's `frame_index` values, by which the report selects the test images (Q-59, Q-63).

## Evaluating a model on a scene

`evaluate_images` evaluates a model on the images of one data split of a multi-view video, for `Trainer.evaluate` now and `ftgs eval` in M14 (Q-68). It renders through `render.render_request`, one request per timestamp, so cameras that share a time render in one call (D-55) and only one time's renders are held at once; it never calls the render backends itself. Its `frame_dt`, which `ftgs eval` sets to a checkpoint's Δt_f, goes to every request as the temporal index's bucket width (Q-174, Q-183); with one time per request, `render_request`'s default never builds the index, so it has no effect until evaluation sends several timestamps per request, which PRD #220 leaves to timing. Each image is evaluated by the `Evaluator` the caller passes, which holds ꟻLIP, with the test image's mask when it has one. The results come back as `ImageMetrics` in the manifest's order, each with its path relative to the manifest, as the metrics report lists them. Given `renders`, a prediction for every record of the split by record index, it renders nothing and scores those instead; `ftgs eval --renders-dir` uses it, so supplied renders and the model's own go through the same evaluator and report (Q-137). A render of the model that isn't finite, NaN or ±Inf in its colors or its alpha, is not scored: E16's clamp would turn an Inf into a plausible color, and the metrics never see alpha. Once the whole data split is rendered, `evaluate_images` raises `FloatingPointError` naming up to five such images in the manifest's order, the error `ftgs eval` and `ftgs train` report as exit 3. A supplied render that isn't finite is input, so it is a `ValueError`, checked before anything is scored, as `read_renders` refuses such a file (Q-129, Q-147).

## Evaluating on several devices

`evaluate_images`' keyword-only `devices` (Q-175, Q-68's note 2) spreads the split's timestamps over shards, one per entry, without changing the results (D-54). `devices=None`, the default, evaluates in the caller's thread with the caller's evaluator, as before. A repeated entry is another shard on the same device, as with `roma_init` (Q-106), and malformed `devices` are a `ValueError` before anything is rendered (Q-186).

Each shard renders its timestamps through `render_request`, one request per timestamp as above, with its own copy of the model on its device, made with the public constructor and keeping `slice_impl`, and scores them with its own `Evaluator`, built by the public constructor on that device. The evaluator the caller passes is then not used: its device is private, and every shard built the same way keeps the shards alike (Q-186). The shards are built in the caller's thread, one after another, before any worker thread starts: each copy's temporal slice runs once there, so the compiled slice is compiled for each device by one thread at a time. ꟻLIP builds its filters and constants on first use on a device and keeps them (the vendored copy's caching, #383); shards that first meet a device together build the same values. With supplied `renders`, the shards only score, and no copy is made. One worker thread per shard takes the timestamps from a shared queue; the results come back in the manifest's order, and a render that isn't finite fails the split with the same error, naming the same images, as without `devices`.

cuDNN's TF32 flag and the float32 matrix-product precision are each one for the whole process. If each metric saved, set and restored them in several threads at once, one thread could restore TF32 while another was computing, and the last could leave IEEE float32's settings behind. A sharded evaluation therefore sets both once, in the caller's thread, around the whole run, and restores the caller's values afterwards, also on an error; each metric's own save and restore then reads and writes IEEE float32's values only, so every metric still runs in plain float32 (D-52).

Three shards on the CPU give exactly the metrics of an unsharded evaluation, and three shards on one GPU equal metrics on gsplat renders; tests check both. The worker threads are `openftgs._shards`' runner, shared with `render_request` and `roma_init` (`docs/modules/render/backends.md`). `ftgs eval` on CUDA passes every visible CUDA device when two or more are visible, and `devices=None` with one (Q-186; `docs/modules/cli/command-line.md`).
