# The frame cache and prefetcher in `openftgs.data`

How D-51 is met: training reads its images from a uint8 copy instead of decoding a PNG at every iteration, and in the sampler's order through a prefetcher. PNG files stay the stable interface (§2.2); `MultiViewVideo.load_image` still decodes them. Layout, placement and the trainer's hook are Q-98's and Q-99's.

## Layout

A cache sits beside its manifest, in `.ftgs-cache/<manifest sha256>/`: one safetensors file per camera with training images, holding that camera's training frames as uint8 [F, H, W, 3] in manifest order. Each file's metadata names the format, its version, the manifest hash, the camera and the record indices of its frames; files are written under a temporary name and renamed. A cache is valid when every file's metadata matches the dataset. A PNG edited under an unchanged manifest isn't detected: rebuild the cache after such an edit. `FrameCache.build` writes a cache, decoding the PNGs with `jobs` threads; `jobs` 0 means the thread budget when `OMP_NUM_THREADS` or `MKL_NUM_THREADS` is set (the smallest positive count among them), else one thread per CPU (Q-215). `ftgs cache` builds it ahead of training and reports its directory and size; with `--placement gpu` or `mmap` it also opens the cache in that placement, to show that it fits or maps, while `auto` leaves the choice to the trainer. A cache that opens on the GPU fits there on its own; a training run also needs room for the model, its growth to N_max and the renderer, which is why "auto" takes the GPU only when the cache fits in half the free memory, once the working memory of a training iteration is set aside, after reserving room for growth (Q-99, Q-223). `ftgs cache` has no configuration, so it can't apply that rule, and a successful `--placement gpu` doesn't promise that training will fit. It never removes the caches of other manifest hashes: two manifests in one folder share `.ftgs-cache/`, and a cache records only its manifest's hash (Q-127).

## Placements

"gpu" loads every camera's tensor into GPU memory; "mmap" leaves the files memory-mapped and reads one frame at a time with safetensors' `get_slice`, so the operating system keeps what it can in RAM. With "auto", a run on the CPU uses "mmap"; a CUDA run decodes its first iteration's image as before, then measures the free GPU memory and chooses "gpu" when the cache fits in half of what is free once the working memory that iteration left reserved (the render's and the losses' buffers at the image's size) is set aside, after reserving room for growth to N_max, else "mmap" (Q-99, Q-223). "off" keeps decoding PNGs. If the cache directory can't be created, "auto" falls back to "off" with a warning, while an explicit placement raises.

## The prefetcher

The sampler's order is known ahead (D-26): its private `peek` returns the rest of the current permutation and the next epoch's, drawn on a copy of the generator's state, so the stream itself never moves (Q-72). The prefetcher keeps `prefetch` images in flight: on CUDA through a ring of pinned buffers copied on a side stream, the training stream waiting on each buffer's event; on the CPU through a reader thread. The worker waits for a ring buffer's previous copy before reusing it, on its own thread. A frame read on the training thread instead (every frame at `prefetch` 0, and a frame taken out of the scheduled order) goes through a fresh block of PyTorch's caching pinned allocator, dropped after its copy: the copy's event is recorded on the block, and the allocator hands the block out again only once that event has completed, checked without waiting, so the training thread never waits on an earlier copy (§2.4 rule 3). The bytes copied are the same. `take` returns float32 values, the uint8 frame divided by 255 on the device, bitwise equal to `load_image`'s. On CUDA the divisor is a 0-dim device tensor: there, dividing by a Python float multiplies by the reciprocal, which differs from the CPU's division in the last bit (Q-99). A resumed run rebuilds the queue from the restored sampler, so it trains on the same images in the same order as a straight run (U-30).

## Measured: B-6 and Q-99's note

B-6 (`ftgs bench data`, `docs/modules/cli/benchmarks.md`) times the data wait, the training stream's `data` stage, against D-51's budget of 1 %, with B-1's configuration at 1M rows on openftgs-synth's kitchen and its 60-frame conversion (Calibration data, #232):

| Placement | Share of an iteration | Data stage, GPU (host) | Budget |
| --- | --- | --- | --- |
| "gpu" (60 frames; kitchen's 23.4 GB cache doesn't fit) | 0.035 % | 0.036 ms (0.03 ms) | passes |
| "mmap", prefetch 8 | 0.035 % | 0.036 ms (0.06 ms) | passes |
| "mmap", prefetch 0 | 0.044 % | 0.046 ms (0.44 ms) | passes |
| "off" | 1.95 % | 2.06 ms (36 ms) | none |

With the cache, the training stream spends its data stage converting the frame to float32. At prefetch 0 the read moved to the training thread, with, when B-6 was recorded, the wait on a pinned buffer's previous copy: 0.44 ms of host time, which runs while the GPU still works through the previous iteration's losses and backward pass, so the stream barely notices. That wait has since been removed (PRD #220's review): the read takes a fresh block of the caching pinned allocator instead. Without the cache, decoding a PNG takes 36 ms of host time, hidden the same way, and the stream copies a float32 image, four times a cached frame's bytes.

"auto"'s rule for the GPU placement (Q-99) was checked at N = 3M rows, the default N_max, with the 60-frame cache (4.37 GiB) on the GPU. After the warm-up iteration it measured 20.31 GiB free and 0.058 GiB of growth, a limit of 10.10 GiB. The run then peaked at 12.09 GiB allocated and 15.23 GiB reserved, 8.57 GiB beyond the cache and the growth from reserved memory (5.43 GiB allocated). That is 84 % of the half of free memory the rule leaves for the iteration's own buffers, LPIPS's activations among them, so a cache at the rule's limit would still have fit, with about 1.6 GiB to spare. The rule stands as it is, and `frame_cache="mmap"` stays the safe setting at the edge of GPU memory.
