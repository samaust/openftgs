Implement the work described in the PRD and/or tickets.

## Finding the PRD and/or tickets

On GitHub, PRDs and tickets usually carry skill labels from the skills that made them:

- `skill:conversation-to-prd` marks a PRD issue published by `/conversation-to-prd`.
- `skill:prd-to-tickets` marks a ticket published by `/prd-to-tickets`.

The reference usually comes with the call: as the skill's argument, or from the step of the owner's sequence that invoked it. Use it to fetch the issue from the issue tracker and state its title before starting; don't list issues or ask which one. If the reference is ambiguous, ask.

If the owner passes no reference, list open issues with those labels; if it isn't clear which PRD or ticket to work on, ask. A ticket belongs to a PRD when it is the PRD's sub-issue, and its blockers are its native "blocked by" dependencies ("Parent issues and blocking" in `docs/agents/issue-tracker.md`). The label alone doesn't tie a ticket to a PRD, because every PRD's tickets share it. A PRD without tickets is implemented as a single ticket, with its Tests that must pass as the acceptance criteria. An issue triaged on its own (no PRD) carries an agent brief comment: the latest one is the contract, giving the acceptance criteria, the scope and the open questions, under the spec.

These are skill labels, not triage labels. Never add, remove or rename them, including when closing tickets. A hand-written PRD or ticket may lack them; the owner's reference wins over the labels.

## Clean room

Follow [docs/agents/clean-room.md](../../../docs/agents/clean-room.md). Log sources and Q-n rows as you go, not at the end, and list the new ones in your final report. A Q-n row is a provisional decision: tell the owner and keep working with it. Stop only for a question you can't settle from the PRD, ticket or spec, a spec contradiction or an incident, and go on with the tickets that don't depend on it. When the owner answers a Q-n row during the run, record the answer on the integration branch as "Answers during a build" in `docs/agents/clean-room.md` says.

## Machine resources

Sessions running this skill in parallel share one machine, and none of them coordinates the others. Together they never ask for more CPU or GPU than it has: two runs that oversubscribe it each go several times slower, not twice, and a timing taken under contention is wrong. They share it through a ledger. `scripts/machine.py` in this skill's folder keeps every run that holds or waits for the machine in `.scratch/machine/` at the root of the main checkout, which every worktree shares, and drops a run once its process ends. Call it as `python3 <checkout>/.claude/skills/implement-without-subagents/scripts/machine.py`, where `<checkout>` is the integration branch's checkout; its docstring gives the details.

- **Inventory.** `machine.py status` prints the physical cores, the GPUs and their memory, the load, every run holding or waiting for the machine (its branch, budget, time so far, estimate and command) and what is free. Check it at the start and before any run that isn't short.
- **Every run goes through the ledger.** Tests, benchmarks and other CPU-heavy commands (`ftgs`, ffmpeg) run as `machine.py run --threads N [--gpu] -C <checkout> -- <command>`. It sets `OMP_NUM_THREADS`, `MKL_NUM_THREADS`, `OPENBLAS_NUM_THREADS` (NumPy's and SciPy's BLAS) and `TORCHINDUCTOR_COMPILE_THREADS` to N for the command and everything it starts, holds the budget until the command ends, and exits with its exit code. Without them, PyTorch's CPU math starts one OpenMP thread per physical core, and idle OpenMP threads spin on cores another run needs. Count what a command starts that these variables don't bound, such as process pools and ffmpeg's own threads. ruff and mypy are short and run without the ledger.
- **Budget.** Ask for at most half the physical cores, so that a session arriving later can split rather than queue behind you; a run expected to take under a minute may take every free core. The owner may change this default.
- **GPU.** `--gpu` holds every GPU for the run, one run at a time. Without it, run only CPU-marked tests (`-m "not gpu"`): the ledger doesn't hide the GPU, since a CPU-marked test checks that torch sees it.
- **Queue or split.** When the budget asked for isn't free, `run` exits 75 and prints the ledger. Estimate which finishes sooner, and do that:
  - *split*: rerun at once with `--threads` set to what is free. That takes about the run's time × N / free when it is CPU-bound, and about its time when much of it goes to work the budget doesn't speed up (start-up, subprocesses, I/O, the GPU);
  - *queue*: rerun with `--wait`, which takes its turn in arrival order and starts once the budget is free. That takes the wait (what remains of the runs that must end first, and of those queued ahead) plus the run's time. Run it in the background and keep working on what doesn't depend on it.

  Estimate from what is known: `machine.py status -C <checkout> -- <command>` lists the command's past runs on this machine with their budgets and times, each run holding the machine shows its time so far and its estimate, and the Calibration data table has the benchmarks'. With nothing to go on, split. Give a run expected to take more than a few minutes `--estimate SECONDS`, so that other sessions can estimate their wait, and re-estimate when the ledger changes. Waiters start in arrival order: a run that fits starts at once unless a waiter ahead of it is short of a resource it would take.
- **Work outside the ledger.** Other skills (`implement-with-subagents`, `two-axis-review`) and the owner's own runs don't register. When `status` notes the load well above the threads the ledger has given out, budget as if those cores were taken.
- **Scope of test runs.** During the work, run only the test files it touches, plus `tests/test_skeleton.py`. The full suites run in steps 5 and 6 through the ledger like any other run, the GPU suite with `--gpu`. They check results, not timings, so unlike `implement-with-subagents`, which owns the machine for its run, they don't wait for an idle machine. A test that passes at the default thread count but fails at another is a finding for the report.
- **Recorded timings.** A benchmark or timing whose numbers go into the repository (the Calibration data table, a stored baseline) runs alone on the machine, at the default thread count: `machine.py run --exclusive --wait` waits until nothing else holds the machine, then holds all of it, the GPUs included, and leaves the thread variables unset. Before recording, check with `uptime` that nothing outside the ledger is running either, since the Calibration rows record the load.
- **Overbudget runs.** If the machine is oversubscribed anyway, stopping your own run and rerunning it within a budget that fits is usually faster than letting it crawl, unless it is nearly done. Another session's run isn't yours to stop.

## Steps

1. Read the PRD and tickets (see "Finding the PRD and/or tickets").

2. Start from a clean working tree: if `git status --porcelain` lists anything, stop and ask the owner what to do with it, since it isn't this work. Then create the **integration branch** from `main`, named after the PRD (for example `prd-<n>-<slug>`), or after the ticket when the reference is a single ticket (`ticket-<n>-<slug>`). If the owner has already set up a branch other than `main` for this work, use it. Never commit on `main` directly. The first commit on the branch holds the clean-room rows this work brings from the tracker, that is, the Q-n candidates and sources consulted listed in the PRD (its Open questions, its Notes and any comments on it) or in a single issue's agent brief. Record each as a numbered row of `docs/clean-room/questions.md` or `docs/clean-room/source-log.md`, ending its Gap or What-was-taken cell with the marker `(from #<issue>: <title>)`. Skip any whose marker is already in those files: an earlier run recorded it ("Where the clean-room files are written" in `docs/agents/clean-room.md`). The same commit applies the PRD's "Glossary and module docs" section to `docs/GLOSSARY.md` and `docs/modules/`, following the `domain-documenting` skill, and skips any entry already there in that form; where an entry conflicts with the spec or with an existing entry, leave it out and ask the owner.

3. Implement each ticket in the order the owner specifies, or in the order they are listed if the owner doesn't specify. If a ticket is blocked by another (its native "blocked by" edges), implement the blocker first. A blocker outside this PRD counts as done if it is closed on GitHub; if it is still open, that ticket and every ticket it blocks can't start: report them and go on with the rest. Call the Skill tool with "tdd" at the seams the PRD and ticket list; its test runs go through the ledger ("Machine resources").

4. Commit as each module or test group goes green: small commits whose messages cite the spec items they implement, any Q-n they rely on and the ticket (`#n`), per CLAUDE.md "Commits". Source-log and Q-n rows go in the same commit as the code that needed them. Stage only the files the work touched, by name; never `git add -A` or `git add .`.

5. Run ruff and mypy regularly, and the test files the work touches, through the ledger ("Machine resources"). Once every ticket that can start is done, if `main` has moved since the integration branch was cut, first merge `main` into the integration branch, resolving any conflict in `docs/clean-room/questions.md` or `docs/clean-room/source-log.md` as "Merging branches" in `docs/agents/clean-room.md` says, so that the tests and the review below run on what will land on `main`. Then run the full CPU test suite, plus the full GPU suite when the machine has a GPU, each through the ledger with the budget "Machine resources" gives it. A ticket whose acceptance tests couldn't run here (GPU-marked tests on a machine without a GPU, dataset-gated tests without the dataset) isn't verified: it stays open, gets a comment naming the tests that didn't run and why, and the report says so. It is verified later as "Unverified tickets" in `docs/agents/issue-tracker.md` says.

6. Call the Skill tool with "two-axis-review", with `main` as the fixed point, so the diff covers every commit on the integration branch. Fix the documented-standard violations and spec findings in further commits, then rerun the full suites of step 5. The judgement calls go in your final report; they don't block the merge.

7. Merge only with the owner's approval. It may already be in the request that invoked this skill (for example "merge each one when its review is clean"); then don't ask again. An approval given in advance doesn't cover unverified tickets, though: if any ticket's acceptance tests couldn't run here, ask anyway, naming each such ticket and the tests that didn't run, and merge only if the owner accepts landing that code on `main` untested. Those tickets stay open either way. Otherwise ask, and start nothing that depends on this merge until they answer. If the owner hands you review findings while you wait for approval (the milestone review of `docs/clean-room/milestones.md`, say), fix them in further commits, rerun the full suites, and ask again. Once approved, merge with `git merge --no-ff <integration-branch>` on `main`, with a merge commit message that names the PRD and its tickets. Never squash: the per-module commits and their spec citations stay in `main`'s history. If `main` has moved again since step 5, don't resolve conflicts on `main`: go back to step 5 (merge `main` in, rerun the suites and the review), then merge. Then ask the owner, as a question of its own: "Push `main` to origin now?" Push (`git push origin main`, nothing else) only if they answer yes to that question; an earlier approval, a merge approval or a request given in advance doesn't count, so ask after every merge. If they decline, go on without pushing, and say in the ticket comments of the next step and in your report that the commits are local only.

8. Close each verified ticket with `gh issue close <n> --comment "..."` pointing to its commits, leaving its labels in place, and close the PRD the same way once all its tickets are closed. Delete the integration branch only after confirming it is merged into `main` (`git branch -d`). Once merged, comment on the PRD (or the single issue) the final number of each candidate this run recorded, one line each: `Recorded: "<title>" → Q-7`. The numbers are final only after the merge into `main`, which can renumber them; tickets that cite a candidate by title are read through this comment. Then, for each new Q-n row from this run, open its decision issue, now that its number is final (every row is provisional until the owner confirms it): title `Q-<n>: <short gap>`, label `q-n`, and the row's spec location, gap, provisional decision, rationale, alternatives and detecting test in the body ("Q-n issues" in `docs/agents/issue-tracker.md`). A row the owner already answered during the run gets its decision issue too, as the record: open it and close it at once with a comment quoting the answer and naming the commit that recorded it.

9. End with a short report: the integration branch, its commits, whether it was merged, the issues closed, the new Q-n rows and source-log rows, the pytest summary of the full runs with each skipped test and why, the tickets left open because their tests couldn't run, the review's judgement calls, and anything stopped or left open. When this skill runs as one step of a sequence, the next step starts from this report.
